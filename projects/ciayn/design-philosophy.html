AI 設計武器樹的哲學

設計原則 · 2026-05-21

頁面邊界

本頁只回答「怎麼設計」：原則、決策樹、AI workflow 與陷阱。它不列完整資料庫，也不盤點目前所有路線；那些分別屬於 game-data.html 與 weapon-tree.html。

核心原則

神器是故事歸宿——是設計的「答案」，先有答案才能反推路徑。

Mechanic 是工程素材——素材要小、紮實、可組合，才能撐起多個不同神器。

路徑（modifier / talent 觸發條件）在中間 meet-in-the-middle，從兩端收斂。

三層結構

玩家在一場 run 中操作的是一把不斷演化的武器，演化過程涉及三層內容：

層觸發點玩家感受內容設計方向Plan 3 範例
Base 武器Lv 1-9 random modifier 3 選 1「我的武器在慢慢成形」Bottom-up — 軸結構正交、可堆疊木棍 → 鐵棍 → 鐵鎚
核心被動 keystoneLv 5 / 15 / 25「我做了一個 build-defining 決策」Top-down — PoE tier 取捨/觸發/最終 mult餘燼蔓延 / 流順之風 / 狂戰士
神器天賦 talentmilestone 後段「我的武器變了個東西」Top-down — 視覺/機制大轉變火焰附身 → 火焰巨人錘形態 → 火焰巨人錘

三層各有專屬職責，互不重疊：

  • Base 武器是建造塊：用 modifier 堆出 shape × material × form 的組合，archetype detection 給每個 cell 一個顯示名稱。內容上限：4 base × 2 material × N shape = 4-8 個基礎 archetype。
  • 核心被動是「Build flavor」決策：玩家走毒系？火系？暴擊流？最終 multiplier 流？三次選擇定下 run 的個性。內容上限：要夠多 keystone 才能讓三次選擇有意義（建議 ≥ 8 個成熟內容池）。
  • 神器天賦是「形態突變」儀式：每次選擇都看得到武器外型/hitbox 有大改變。內容上限：每個 base family 至少 1 條神器路徑（最終目標 4 family × 2-3 路徑 = 8-12 個 artifact archetype）。

Top-down

適用場景：設計新神器（archetype）、新 keystone、新 talent。

  • 玩家「終局體驗」優先
  • 視覺與機制的高潮優先
  • 反推所需 tag / stat / 觸發條件

不適用場景：底層 mechanic、stat pipeline、event hook、refactor 既有系統。

  • 這些需要 bottom-up
  • 從重用性、composability 反推
  • 不要為單一神器寫死

Top-down 三步驟

  1. 畫終形：先寫神器的 archetype 定義（名稱、flavour、視覺、stat 大改、tag 需求）。

```

id: archetype_fire_giant_hammer

display_name: 火焰巨人錘

flavor: 金屬長柄錘燃成熔爐，每次重擊推出三段震波。

match: [#長兵, #金屬製, #打擊, #重擊, #火, #火焰巨人錘]

unique mechanic:

shockwave_3phase

radii 120 / 200 / 300

damage ×1.5 / ×1.0 / ×0.6

```

  1. 反推所需 tag：archetype match 需要哪些 tag？哪些是 base family 自帶（#打擊 #重擊），哪些需要元素（#火），哪些需要神器簽名 tag（#火焰巨人錘）？
  2. 反推 talent 內容：誰來授予這個 special tag？怎麼授予（inline synthetic mod / 直接 grant）？對應的 talent 要如何 fit 進現有 milestone pool？

Keystone 的 top-down 三型

核心被動 keystone 是 PoE-tier 設計，不是純屬性 buff。用三種 archetype 風味驅動設計：

  • 取捨型：放棄 A 換爆 B。例：狂戰士（傷害 ×1.5 但受傷 ×1.5）。玩家感受「我選擇了極端」。
  • 條件觸發型：滿足前置 mechanic 後爆發新行為。例：餘燼蔓延（點燃敵死亡時擴散）、暴擊連鎖（暴擊後 1.5s 必爆）。玩家感受「我啟動了一個新規則」。
  • 最終 multiplier 型：所有 stack 後再乘一次。例：流順之風（攻速/移速 ×1.25）。玩家感受「我繞過了 stack decay」。

> 反模式：「攻擊速度 +15%」「最大生命 +20」這種純屬性 buff不應該放進核心被動 pool。它們屬於 Lv 1-9 random modifier pool 的職責。核心被動每一格都應該是一個「我能跟朋友講」的決策——「我這場選了餘燼蔓延，火焰擴散爽炸」遠勝「我選了 +15% 攻速」。

Bottom-up

適用場景：底層系統設計、refactor、新 event hook、stat pipeline 擴展。

  • 重用性 > 單一場景
  • API 簡單、小、composable
  • 多個 keystone 共用

不適用場景：內容（神器、keystone、talent）的設計。

  • 內容需要 top-down「先有答案」
  • bottom-up 容易設計出「可組合但沒人用」的素材

Bottom-up 三步驟

  1. 從多個 top-down 需求倒推共同 primitive：餘燼蔓延需要 on_enemy_died event；暴擊連鎖需要 on_attack_resolved(is_crit) event；都需要 weapon → keystone 的事件管道。
    → primitive: weapon 加 attack_resolved signal + EnemyBase.died(snapshot) extended signal。
  2. 檢查「能不能 abstract 成可重用的 hook」：餘燼蔓延的 spread API 不能寫死「只給火用」——要設計成 spread_status_in_radius(status_id, radius, max_n)，未來毒擴散、雷擴散都能用同一個 API。
  3. 實作最小可行版本，先讓一個 top-down 需求跑通：不要為了「將來可能有的 4 種 element」寫一個 generic StatusSystem class。先讓 ignite 用最簡單的方式跑通（reuse 既有 apply_dot），需求變多時再 abstract。

Plan 3 的 bottom-up 戰利品

Primitive誰用它未來可重用
mul_final stat op流順之風、狂戰士、巨化神器化、鎚的精通任何「最終結算再乘一次」的 keystone / talent
EnemyBase.died(self, snapshot)餘燼蔓延（讀 snapshot.was_ignited）任何 on-kill keystone（屍爆、收割、reset cooldown）

Meet-in-the-middle

Top-down 從「神器」推下來，bottom-up 從「primitive」推上去。中間是「玩家從木棍走到神器」的路徑——這條路徑由 random modifier + talent + keystone 共同組成。設計時兩端逼近：

│   Top-down 神器：火焰巨人錘 [#長兵 #金屬製 #打擊 #重擊 #火 #火焰巨人錘] │
│                              ▲                                  │
│                              │ 反推: 缺神器簽名 tag             │
│                              │                                  │
│              ┌───────────────┴───────────────┐                  │
│              │ talent_grant_fire_giant_hammer│ ← top-down 設計  │
│              │ 授予簽名 tag + shockwave 行為 │                  │
│              └───────────────────────────────┘                  │
│                              ▲                                  │
│                              │ Lv 20 milestone roll             │
│                              │                                  │

路徑設計的兩個方向逼近原則：

  1. Top-down 端：寫好神器後，列出所有需要的 tag。每個 special tag 對應一個 talent；每個 base tag 應該已經被 modifier pool 涵蓋。
  2. Bottom-up 端：random modifier pool 已存在的內容（金屬化、加長、重塊...）能組合出哪些 base archetype？哪些 cell 還缺？補相應 modifier。
  3. 對接點：milestone pool 的 affinity 機制是橋樑。Lv 10 拿了烈焰附身 → 武器有 #火 → Lv 15 keystone roll 時餘燼蔓延 affinity 命中 → 玩家自然走進「火焰 build」。

具體 checklist：設計新神器（archetype）

  1. 寫 flavour + 視覺描述（top-down 起點）
  2. 列 archetype match tags（哪些 base / 哪些 special）
  3. 每個 special tag — 對應的 talent 已存在？沒有就新增
  4. 每個 base tag — random modifier pool 能堆出來？沒有就補 modifier
  5. 所需 stat 改變 — 既有 mul / mul_final / set 夠用？需新增 stat 就在 axes-schema 加
  6. 新增 archetype 到 archetypes.json + 同步 weapon-tree.html（AGENTS.md 規定）
  7. 加 archetype detection 整合測試

具體 checklist：設計新 keystone

  1. 選一個 keystone 風味（取捨 / 條件觸發 / 最終 mult）
  2. 寫 flavour + 一句話描述（玩家拿到的爽感）
  3. 列觸發條件 — 既有 hook (attack_resolved / died.snapshot / tick) 夠用？沒有就加
  4. 列 affinity tags — 跟哪些 weapon tag 共鳴？（影響 saving throw 命中）
  5. 寫 GDScript class extending KeystoneBase
  6. 加進 milestone_keystones.json + MilestoneApplier.KEYSTONE_REGISTRY
  7. 加 unit test

具體 checklist：設計新底層 mechanic

  1. 找出 2+ 個 top-down 內容需求都需要這個 mechanic（< 2 就不要做）
  2. 定義 API — 名字、參數、副作用，盡可能 small + composable
  3. 不要為單一神器寫死。問自己：「下一個 element / 下一個 keystone 會用嗎？」
  4. 實作 + 寫至少 1 個 consumer 的 demo 才能 commit
  5. 更新本文檔，把 primitive 加進「bottom-up 戰利品」表

常見陷阱

陷阱 1: keystone 為單一機制寫死

餘燼蔓延的「spread」邏輯如果寫成「只給火用」，未來毒擴散就要再寫一份。正確做法：把 spread API 設計成 spread_status_in_radius(status_id, radius, max_n)，keystone 只 declare「我要傳 status X」，spread 怎麼找目標是共用的。目前 Plan 4B 仍是 ad-hoc per-status implementation：burn / ice / poison / blood 各自有清楚的最小路徑，避免過早抽象。五個 status 上線後，TODO-003 才是評估共用 StatusSystem / spread primitive 的時機。

陷阱 2: 過早抽象 generic StatusSystem

Spec 原本想做 generic EnemyBase.statuses: Dict[StatusId, StatusInstance] 容器。Plan 3 只有 ignite 一個 status——抽象出來反而 over-engineering。實作時降級為 _ignited_remaining: float flag + reuse DOT pipeline。Plan 4B 已擴到 chill / shock / poison / bleed，但仍先用 ad-hoc API ship 完整 gameplay path。原則：第一個需求 ad-hoc；第二個以上需求出現時先累積對比樣本，再用實際重複形狀抽象，而不是預先發明通用容器。

陷阱 3: milestone pool 把純屬性 buff 跟 keystone 混在一起

如果 Lv 5 keystone 池有「攻速 +15%」也有「餘燼蔓延」，純屬性會稀釋決策感。Lv 1-9 random modifier 才是純屬性的家。Plan 3 設計：keystone pool 5 個都是 PoE-tier 取捨/觸發/最終 mult，沒有純數值。

陷阱 4: 神器 archetype 沒有明確標示適用路徑

神器不是「任何武器拿到一個酷 tag 就應該成功」。每個神器都要明確標示適用路徑：需要哪個 shape、material、edge/form、element，以及哪個 signature tag。若路徑沒有寫清楚，玩家會以為自己能轉職，實際上 archetype detection fail。教訓：top-down 設計神器時，要明確標示「適用 base」與 signature tag；相鄰 family 若也應該有終形，就另外設計專屬神器，而不是讓一個神器模糊套用。

陷阱 5: signal 擴充 arity 沒同步 callers

Plan 3 把 EnemyBase.died(self_ref) 改為 died(self_ref, snapshot)。Godot 對 lambda func(_e): 強制 arity match，舊 callers 會 silent fail。原則：改 signal arity 時 grep 所有 callers 一起改。Plan 3 main.gd:128 是唯一既有 caller，已同步。

陷阱 6: 新 class 用 class_name 全域註冊

Godot 4 headless 模式對新加的 class_name 全域註冊有延遲。Plan 3 為此踩了 3 次 parse error。

解法：新 class 用 extends RefCounted 或 extends Node 不加 class_name；其他檔案用 preload("res://path/to/class.gd") 引用。

陷阱 7: 材質 ecosystem 不對稱（Plan 4 grill #17）

設計三材質時若每個材質帶的「機制負擔」不一樣，會造成 ecosystem 嚴重失衡。Plan 4 grill 期間發現：

骨製自帶 #流血 (auto-DOT on hit) + 一個 keystone (爆血) = 1 keystone-worth；

結晶只有「元素 ×1.5」的 multiplier，沒有自己的 keystone family（共用 4 個元素 keystone）；

金屬純物理 power，沒 keystone。

這讓骨製感覺「自帶完整 build」而結晶/金屬感覺「只是 stat 修飾」。

教訓：每個材質定 ecosystem 時要對齊「附帶機制深度」——可用 talent/keystone 數量、或 stack path 數量計算對稱性。Plan 4B 補上 2 個骨製友善 talents (talent_bone_spike, talent_bleed_amp) 部分補償，但底層 asymmetry 仍在。下一輪內容 (Plan 5+) 設計新材質時要先 audit ecosystem，再寫 spec。

陷阱 8: chain demo N=1 — AI extrapolation fragile（Plan 4 grill #17）

Plan 4 的法杖 vertical slice 是唯一的 chain demo (#短小 → #投射物 → #環繞)。當 chain endpoint 只有一個範例時：

  • AI 看到 N=1 不知道哪些屬性是 chain pattern 本質、哪些是這一個 archetype 的偶然細節
  • /design-weapons skill 用 1 個 template 生 chain-end 候選，傾向過擬合到法杖的具體 stat / flavor / form 組合
  • 設計師複用 chain 機制時也容易把法杖的偶然約束（必須結晶？必須短小？必須元素？）當成 chain 通則

教訓：chain endpoint 屬於「需要 N≥2 對比範例才能設計穩定」的內容類別。Plan 4 ship 完整 8 specials 後，TODO-003 排上 #光環 / #追蹤 form 設計，把 chain demo 推到 N=3，再啟動 AI extrapolation。

在那之前，AI 生 chain-end 候選時 prompt 要明確標記「chain pattern fragile, N=1」，並要求 G4 human review 特別關注 chain 屬性的歸納。
